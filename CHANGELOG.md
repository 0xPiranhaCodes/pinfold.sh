## [Unreleased]

### Security

- On Linux a protected pane no longer reads as unprotected while a program is starting ([#336](https://github.com/0xPiranhaCodes/pinfold.sh/issues/336)). Between `execve` giving a process its new name and setting out its arguments, `/proc/<pid>/cmdline` is empty, which `foreground` returned as an empty command line that no `api.protect` pattern matches, so `pane.send` could go through; the name could also be read after the exec and the arguments before it. An empty `cmdline` now reads as none, the name and user are read on both sides of the arguments and must agree, and both cases get the 4 tries 1 ms apart macOS already had, then read as unreadable, which protects the pane. A process that exited but was not reaped reads as exited, as on macOS. `the_foreground_process_has_its_name_arguments_and_user` failed 100 of 1600 runs, 16 at a time in Docker on Linux (aarch64), with `Some([])`, and 0 of 1600 after (`tests/linux/foreground-loop.sh`); it now also waits until the arguments can be read.
- A sandboxed agent can no longer use the clipboard directly ([#328](https://github.com/0xPiranhaCodes/pinfold.sh/issues/328), [ADR-0041](docs/adr/0041-sandbox-hides-writes-not-secrets.md)). On macOS the profile denies `mach-lookup` of `com.apple.pasteboard.1` and `com.apple.coreservices.uauseractivitypasteboardclient.xpc`, the services `/System/Library/LaunchAgents/com.apple.pboard.plist` lists for `/usr/libexec/pboard`, and of Universal Clipboard's `com.apple.coreservices.uasharedpasteboard*`; `pbpaste` and `pbcopy` exit 1 inside it. On Linux the agent no longer gets `DISPLAY`, `WAYLAND_DISPLAY`, `WAYLAND_SOCKET` or `XAUTHORITY`, `~/.Xauthority` joins the hidden stores, and its fresh `/tmp` and `$XDG_RUNTIME_DIR` already hide the X11 and Wayland sockets. An X server's abstract socket is scoped only with Landlock ABI 6, as before (ADR-0038), so below it an X server that admits the user without a cookie still serves the clipboard. `a_sandboxed_agent_cannot_reach_the_clipboard` runs the real `sandbox-exec` or bubblewrap: on macOS it puts a mark on the pasteboard and checks the agent can neither read nor replace it, then restores your text, and skips with a reason where there is no pasteboard; on Linux it plants display sockets and checks none connects. `a_sandboxed_agent_keeps_the_network` checks the network stays open, connecting to `example.com:443`, and skips with a reason when the test machine cannot reach it either.

- A sandboxed agent no longer gets environment variables whose names look like secrets ([#328](https://github.com/0xPiranhaCodes/pinfold.sh/issues/328), [ADR-0041](docs/adr/0041-sandbox-hides-writes-not-secrets.md)). Before exec, `sandbox::command` removes every variable whose name holds `TOKEN`, `SECRET`, `PASSWORD`, `PASSWD`, `CREDENTIAL` or `APIKEY`, ends in `_KEY` or `_PAT`, or starts with `AWS_`, in any case (`sandbox::secret_name`), reading names only. An agent profile's new `keep_env` names the ones its agent still gets, such as `ANTHROPIC_API_KEY`: at most 16 exact names of letters, digits and `_`, checked when the config is read. `a_sandboxed_agent_gets_no_secret_variables_but_those_it_keeps` runs `env` under the real `sandbox-exec` or bubblewrap with five such variables set, one of them kept; it fails when a stripped one is kept. A sandboxed agent CLI that reads its API key from the environment needs `keep_env` from now on.
- A sandboxed agent can no longer read the common credential stores ([#328](https://github.com/0xPiranhaCodes/pinfold.sh/issues/328), [ADR-0041](docs/adr/0041-sandbox-hides-writes-not-secrets.md), now accepted by the maintainer's decision of 2026-11-09). `pinfold_config::credential_stores` lists `~/.aws`, `~/.azure`, `~/.docker`, `~/.gnupg`, `~/.kube`, `~/.netrc`, `gcloud` and `gh` in `~/.config` and `$XDG_CONFIG_HOME`, and this system's browser profiles (7 on macOS, 10 on Linux), and `private_dirs` adds them to what the sandbox hides. On macOS `sandbox-exec` denies reading each, resolving a missing one through its parent; on Linux bubblewrap mounts an empty directory over each directory and, new, `/dev/null` over each file, and skips a missing one. `a_sandboxed_agent_cannot_read_credential_stores` puts a secret in each store but one and runs the real `sandbox-exec` or bubblewrap; it fails with every secret printed when the stores are not hidden. A tool that needs a hidden store, such as `aws` or `gh`, now fails inside the sandbox. `pinfold-core` gains `pinfold-config` as a dev-dependency.
- On macOS a sandboxed agent can no longer start a program outside its sandbox ([GHSA-f24m-hqgq-vp7v](https://github.com/0xPiranhaCodes/pinfold.sh/security/advisories/GHSA-f24m-hqgq-vp7v)). The `sandbox-exec` profile allowed LaunchServices launches, so an agent could write an app bundle into its working directory and `open` it, and launchd started it as an ordinary process of the user, with none of the sandbox's rules. The profile now denies `lsopen` and `appleevent-send`; `open` fails with LaunchServices error -54. `a_sandboxed_agent_cannot_start_an_app_outside_its_sandbox` runs the real `sandbox-exec`, opens such an app that writes outside the working directory, and fails without the fix. Under the new rules `python3`, `node`, `git`, `claude` and `curl` still run. Linux is not affected.

### Fixed

- A damaged font can no longer reach undefined behaviour in `zeno`, the rasterizer under `swash` ([#310](https://github.com/0xPiranhaCodes/pinfold.sh/issues/310)). zeno converts each outline point with `to_int_unchecked`, which is undefined for NaN and values outside `i32`. It first shifts points by the outline's bounds, and `pinfold-render` already measures every glyph and refuses one wider or taller than its cells allow, so finite points stay in range; but `bounds` skips NaN points. `extent` now refuses an outline with a NaN or infinite point, as it refuses one too large for its cells: from the chosen font such a glyph draws blank, from a fallback font the missing-glyph box shows instead, and a font with one in ASCII is not used. Outlines come from integer font data scaled by a size of 4 to 256 pixels, and no font is known to produce one. `only_finite_outlines_reach_the_rasterizer` covers the check.
- On Wayland, pasting a huge clipboard no longer grows the window ([#310](https://github.com/0xPiranhaCodes/pinfold.sh/issues/310)). smithay-clipboard 0.7.2, which copypasta uses, appends another client's whole selection offer to a `Vec`, as 0.7.3 still does. It is now vendored in `vendor/smithay-clipboard/` with a patch that stops reading past 1 MiB and fails the load with `ErrorKind::FileTooLarge`, into a buffer made that size once; `pinfold-sys` turns that into the "Paste refused: over 1 MiB" row. `vendor/check.sh` checks both forks against their published crates, and the Nightly workflow watches RustSec for both. `a_wayland_offer_past_the_limit_is_too_large` covers PinFold's side; no test drives a real compositor, as reading a selection needs keyboard focus.
- On X11, pasting a huge clipboard no longer grows the window, and a hostile requestor can no longer stop copies from working ([#310](https://github.com/0xPiranhaCodes/pinfold.sh/issues/310)). x11-clipboard's `load` collects a whole INCR transfer, and reserves the size the owner announces, before its caller sees a byte. The window now reads through its own X11 connection (`pinfold-sys/src/clipboard/x11.rs`), asking the server for at most 1 MiB and a word each time and counting INCR chunks into room that never grows, so past the 1 MiB paste limit it shows the "Paste refused: over 1 MiB" row. Each read opens its own connection and window, as ICCCM cannot end an INCR transfer: an owner whose transfer was refused writes its next chunk whenever the property is deleted, which mixed into the next read in 2 of 4 runs when one window was reused. It waits on the connection with `poll` rather than x11-clipboard's 50 ms sleeps, and read 4 MiB by INCR from `xclip` in 15.5 to 35.7 ms in 10 of 10 passing runs of `tests/window/clipboard.sh`, which runs the display tests under Xvfb; CI's Linux mem-gate job now runs them too. x11-clipboard serves copies from a thread whose `value.len() - pos` underflows when a copy replaces a long text during another client's INCR transfer, as it keeps one transfer per property name. The test reproduces it: the thread panics at `run.rs:189`. The window unwinds, so only that thread ends, but every later copy failed; a copy that fails now reconnects once and retries (`copies_work_again_after_a_requestor_ends_x11_clipboards_thread`). `pinfold-sys` depends directly on `x11-clipboard` and `x11rb`, at the versions copypasta already builds.
- On macOS, pasting a huge clipboard no longer grows the window ([#310](https://github.com/0xPiranhaCodes/pinfold.sh/issues/310)). AppKit reads a whole pasteboard into the process that asks, before its size is known: reading a 64 MiB one that another process wrote took this process from 2 MiB to 131 MiB (`appkit_reads_a_whole_pasteboard`, ignored, run by hand). The window now runs `/usr/bin/pbpaste` with `LANG=en_US.UTF-8` and reads at most 1 MiB and one byte from its pipe, so past the 1 MiB paste limit it shows the existing "Paste refused: over 1 MiB" row and allocates no more; a 64 MiB clipboard grew the test process by 1,179,648 bytes (`a_large_clipboard_costs_this_process_the_limit`). A `pbpaste` still writing after 3 seconds, as copypasta waits on X11, is killed and the paste does nothing. This also keeps copypasta's `types().unwrap()`, which panics when the pasteboard has no types, out of the window. Copying a file in Finder now pastes the text `pbpaste` gives for it, where copypasta read the file URL and pasted the path. Copying still goes through copypasta. X11 and Wayland follow in their own pull requests.
- Dependabot's pull requests pass the DCO check. A commit skips the sign-off check only when its pull request was opened by `dependabot[bot]` and its author email is `49699333+dependabot[bot]@users.noreply.github.com`; the pull request's opener comes from the event, which a commit cannot forge. A forged Dependabot author on a human pull request, and a human commit without a sign-off on a Dependabot pull request, still fail. `.github/scripts/test-check-dco.sh` covers six cases and runs in the `dco` job.
- Help, Edit Config and Open Link no longer find `xdg-open` through `PATH` ([#298](https://github.com/0xPiranhaCodes/pinfold.sh/issues/298)). An executable named `xdg-open` placed early in the `PATH` PinFold inherited ran instead of the desktop's opener. On Linux and other Unix the window now runs the first of `/usr/bin/xdg-open`, `/usr/local/bin/xdg-open` and `/run/current-system/sw/bin/xdg-open` (NixOS) that is a regular, executable file once symlinks are followed, and otherwise writes `pinfold: cannot start the opener: no executable opener at` and the three paths to stderr. macOS still runs `/usr/bin/open`. The target stays one argument with no shell, and the environment is kept, as openers need the session's display and D-Bus variables. A test gives the opener a `PATH` holding a fake `xdg-open` and checks it never runs.
- The audit log file can no longer be redirected by a symlink swapped in at its path ([#299](https://github.com/0xPiranhaCodes/pinfold.sh/issues/299)). It was checked with `symlink_metadata` and then opened by path, so a symlink put there between the two was followed, and the target was written and made 0600. It is now opened once with `O_NOFOLLOW | O_NONBLOCK | O_CLOEXEC`, the open file must be a regular file owned by the user, and its mode is set through the descriptor; rotation opens the new file the same way. Its folder must be owned by the user and not group or world writable, as `state_dir` is created 0700, so no other user can swap entries in it. A test swaps a file and a symlink at the path while opening 2,000 times and checks the target is never written or chmodded; it fails without `O_NOFOLLOW`. `pinfold-api` gains `libc`, at the version `pinfold-sys` and `pinfold-config` already use.
- `a_core_started_with_no_shell_exits_if_no_window_ever_opens` starts its clock before it spawns the core, not after `start_core` returns ([#295](https://github.com/0xPiranhaCodes/pinfold.sh/issues/295)). `start_core` also writes the core's pid file after the spawn, and the core starts its 2 s empty wait as soon as it is running, so a test thread that stalled past the core's startup measured less than 2 s and failed with "it did not wait for a window", as on CI at a34c5f0. The core is right: its wait never ends before 2 s after its own start. On an arm64 Mac the core starts its wait 107 to 133 ms after the old clock under 16 busy loops, and a 300 ms sleep put after `start_core` made the old test fail 19 of 20 runs with that message and the fixed one 0 of 20. Behaviour is unchanged. `crates/pinfold-cli/tests/repeat.sh 100 --exact a_core_started_with_no_shell_exits_if_no_window_ever_opens` passed 100 of 100 under 16 busy loops.
- The launcher reports a core killed before it answered at once, with the signal, instead of waiting 5 seconds and saying no core answered ([#288](https://github.com/0xPiranhaCodes/pinfold.sh/issues/288)). That is what the two `session` flakes of #288 were: on an arm64 Mac, Gatekeeper (AppleSystemPolicy) sometimes kills an unsigned program that the tests place in a temporary folder at exec, and logs `Security policy would not allow process`. A killed `pinfold-core` made `a_window_that_exits_during_start_fails_the_launcher` say "no core answered", and took the pane of `mcp_lists_tools_…` with it, so that test waited its full 120 seconds. That test now fails at once when its core ends. Killing the core at exec on purpose reproduces both: 5.09 s then "no core answered", and a 120.03 s wait. Neither test failed when run alone, 0 of 200 runs each idle and 0 of 200 under 16 busy loops. In 100 runs of the whole binary neither failed, but one denial killed another test's launcher (SIGKILL, empty stderr). The denials stop once the terminal's app is a Developer Tool, which `CONTRIBUTING.md` now says. `crates/pinfold-cli/tests/repeat.sh` runs the loop and lists the denials.
- Two CI flakes are fixed at their cause ([#286](https://github.com/0xPiranhaCodes/pinfold.sh/issues/286)). The esctest driver now reads EIO from the PTY as the end of output: Linux returns it once the program closes the terminal, which happens during exit before the program can be waited for, so the old `try_wait` check could miss it. In an `rust:1-bookworm` container, a loop of `esctest-driver sh -c 'printf "%04000d" 0'` failed 25 of 2000 runs before the fix and 0 of 2000 after. `an_updated_window_restarts_a_core_at_a_prompt_and_opens` now gives its pane a shell that is at its prompt from the start. A login `/bin/sh` runs `/etc/profile`, whose `path_helper` on macOS the core correctly counts as a program a restart would end. The flake did not reproduce on an arm64 Mac (0 of 200 runs alone, 0 of 50 runs of the whole `session` binary), but a shell that forks `sleep 1` at startup made the old test fail 2 of 3 runs with `pane 0: sleep`. After the fix it passed 100 of 100 runs alone and in all 100 runs of the whole binary. Behaviour is unchanged.
- The `.dmg`'s root folder is 0755, not the 0700 `mktemp -d` gave its staging folder, and `dmg.sh` copies a Finder icon layout from `packaging/macos/dmg.DS_Store` when one is committed ([#279](https://github.com/0xPiranhaCodes/pinfold.sh/issues/279)). Finder writes that file, so `packaging/macos/dmg-layout.sh` made it once on the maintainer's Mac, which has a screen and Automation access to Finder; CI has neither. The file is committed. Run here, its Finder script waited past 60 seconds, as macOS asked for that access on screen.
- PinFold opened from its disk image no longer breaks when the image is ejected ([#279](https://github.com/0xPiranhaCodes/pinfold.sh/issues/279)). On macOS the launcher refuses to run from a read-only volume, which a `.dmg` and App Translocation's mount both are, and says to drag PinFold to Applications, in a dialog when the Dock started it. A core from another copy of PinFold, such as beta.1's on a mounted image, is restarted from this copy if the person agrees, through ADR-0043's restart. A core that does not answer `hello` and `window.open` within 12 seconds, down from 62, gets SIGTERM, then SIGKILL after 5 seconds, and the launcher starts its own core, which restores the session as last saved. Only a peer with this user's UID, at the session's socket, named `pinfold-core` is signalled. The restart waits until its connection closes as well as the socket refusing, as a hung core's full backlog refuses too. On this Mac, beta.1's core hung at about 190% CPU after `hdiutil detach -force` and ignored SIGTERM; the new launcher recovered in 17, 18 and 17 seconds in three runs of `tests/macos/dmg-eject.sh`. The drag that did not move is not reproduced.
- `pinfold-sys` gains what the launcher needs to recover from a core whose disk image was ejected ([#279](https://github.com/0xPiranhaCodes/pinfold.sh/issues/279)): `kill_peer` sends SIGKILL to a socket's peer as `terminate_peer` sends SIGTERM, `peer_executable` and `peer_name` give its program's path and the kernel's name for it, and `read_only` says whether a path is on a read-only mount, as a `.dmg` and App Translocation's mount are. On macOS a core whose image was force-ejected has no path (`proc_pidpath` fails with ESRCH) but keeps its name, `pinfold-core`. Nothing calls them yet.
- [ADR-0045](docs/adr/0045-tools-are-programs-in-their-own-pane.md), accepted by the maintainer on 2026-11-09, designs the v0.2 built-in tools (M4). The markdown reader, file manager and diff viewer become `pinfold md`, `pinfold files` and `pinfold diff`, full-screen programs that the core starts in their own pane through a new `tool.open` method, so a tool cannot take down the core or the window and returns its memory by exiting. They draw with their own cell writer instead of `ratatui`, parse markdown with `pulldown-cmark` and diffs from the user's `git` through one hardened entry point, escape control and bidi characters, cap size and time, and refuse `pane.send` from any API caller. The ADR states memory targets per tool, the fuzz, snapshot and golden-image tests, and 15 slices of about 400 lines, opened as #311 to #324 plus #262 in the "M4: built-in tools" milestone, with #233, #235 and #263 moved there. `docs/spikes/m4-tools/` holds the scripts behind its numbers: of the candidate crates, `ratatui`, `syntect` and `notify` fail `cargo deny` under our policy, and an idle `pinfold mcp` uses 2.10 MB on macOS. ADR-0003 is superseded in part, as the window no longer hosts the tools, and `architecture.md` and the threat model describe tools as programs in their own pane instead of an in-process `Tool` trait drawn with `ratatui`. Behaviour is unchanged.
- [ADR-0044](docs/adr/0044-cores-without-the-hardened-runtime-warn.md), Proposed, asks whether a macOS core without the hardened runtime, such as a `cargo` build, warns or refuses a session ([#109](https://github.com/0xPiranhaCodes/pinfold.sh/issues/109)). A running core can read its own flag with `csops(CS_OPS_STATUS)`: `tests/hardening/runtime-flag.sh` shows `CS_RUNTIME` clear in a `cargo` build of `pinfold-core` and set once `bundle.sh` signs it. The ADR proposes a warning in the window plus a status-bar marker, with the ad hoc `codesign -o runtime` command that fixes a source build. Behaviour is unchanged.
- A pane whose shell command finished keeps showing ✓ done or ✕ error at the next prompt until another command runs ([#236](https://github.com/0xPiranhaCodes/pinfold.sh/issues/236)). Shells send the prompt's OSC 133 `B` mark in a later read than `D`, so before this the pane went back to ○ idle within a few milliseconds and done or error was almost never seen; `pane.list` and `pane.status` events now say `done` or `error` there instead of `idle`. Recorded sessions of Claude Code 2.1.311 and codex-cli 0.166.0 in `crates/pinfold-core/tests/agent_sessions/` replay through the VT engine and status engine and must show `idle, running, done, running, error`; `record.sh` re-records them, and the test fails on a fixture over 200 KB or holding a home path, email address, `sk-` key, host or user name. A CLI waiting at its own permission prompt still shows running ([#276](https://github.com/0xPiranhaCodes/pinfold.sh/issues/276)).
- Golden images cover the CPU renderer's output ([#232](https://github.com/0xPiranhaCodes/pinfold.sh/issues/232)). `crates/pinfold-ui/src/golden.rs` draws plain text, wide characters with the cursor on one, bold, italic, inverse and colours, pane borders, the bar (one image per system) and an approval prompt at 26 pixels with the bundled font alone, and compares each with a PNG in `src/golden/`, allowing 2 per channel. A failure writes the actual image and a diff beside the reference; `PINFOLD_UPDATE_GOLDEN=1 cargo test -p pinfold-ui golden` rewrites them. `Fonts::alone` gives a painter no fallback fonts, `Painter::new` takes it, and `cells_with_cursor` is public. `pinfold-ui` gains `png` as a dev-dependency, with `safe-to-run` cargo-vet exemptions for it and the 8 crates it brings, and typos accepts `flate`, from `flate2`. The renderer has no underline or cursor shapes, so they have no images.

### Fixed

- macOS: frames share one Metal instance buffer, so the window's idle memory reads steadily.
  The window budget rises to 33 MB plus pixels (ADR-0030).
- A core test that failed on macOS when its stand-in window had already ended.
- `pinfold` waits until the window is on screen, and fails with a short reason if the window cannot run, ends during start or is not ready in time: 10 seconds for a core's first window, so a slow Mac does not report failure for a window that opens, and 2 seconds after that. It used to exit 0 once the process existed, and said only "no window can open".
- Bold `i` and other glyphs of several contours no longer come out thinner than regular.
- A paste or a key no longer vanishes while the core lags. The window waits for the link in order, holding at most about 3 MiB, and past that says so under the pane, as it does for input a stalled program has no room for. A paste over the 1 MiB limit, less its brackets, is refused with a note instead of going missing. The link's version is now 4.
- Fallback font pages no longer count against the window once a frame is drawn.
- A copy of a whole pane can run in steps, which keeps its text out of the core's footprint.
- A core started by `pinfold`, and its windows, write problems to `default.log` in the runtime directory, so a window that dies says why even from the Dock, and a failed `pinfold` names the file. It is private, starts empty with each core, and a panic there prints only its place, as a panic's text can quote a pane.
- A window taller than 24 rows no longer costs the core about 2 MB, as growing a grid makes only the rows it needs.
- The core sends a window only the panes it asked for, so a hidden pane holds no frame.
- The config file is `pinfold.toml`, the name the design gives it.
- Closing a pane with unread output can no longer hang on macOS.
- A window narrowed to one column with a wide character on screen no longer exhausts memory.
- An unterminated OSC string can no longer grow the core without limit.
