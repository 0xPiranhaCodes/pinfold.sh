## [Unreleased]

### Security

- `a` in `pinfold diff` sends the hunk at the top of the view, with a typed comment, to the last focused agent pane's prompt as review feedback ([#323](https://github.com/0xPiranhaCodes/pinfold.sh/issues/323), [ADR-0045](docs/adr/0045-tools-are-programs-in-their-own-pane.md)). It reuses `@`'s target and `pane.send`, so the window approves it like any cross-pane send, showing the exact text, and a denial sends nothing. The comment is typed in a prompt drawn in the pane; pasted text never reaches it, and only Enter sends. The text is the comment, the file name, the hunk header and the hunk lines, joined by ` ␤ ` (U+2424) into one line, each escaped as the screen shows them (control and bidi characters as `^X` and `<U+202E>`, tabs as `^I`), since the hunk is untrusted repository content going into an agent's prompt. It holds at most 200 hunk lines and fits `pane.send`'s 4096 bytes beside a comment of at most 512 escaped bytes; a last line says how many lines were cut. It holds no newline anywhere, so nothing is submitted, even if the pane's foreground program reads lines, as a shell does. No API caller can press `a`, as `pane.send` to a tool pane is refused. No new crates.
- `pinfold files` rename, move and trash never replace a name made after their check ([#374](https://github.com/0xPiranhaCodes/pinfold.sh/issues/374)). The rename itself refuses a taken name: `renameat2` with `RENAME_NOREPLACE` on Linux and `renamex_np` with `RENAME_EXCL` on macOS, through the new `pinfold_sys::rename_no_replace`. A Linux file system without `RENAME_NOREPLACE` is refused rather than renamed with a race.
- `@` in `pinfold files` types the marked paths, or else the selected one, into the last focused agent pane's prompt ([#320](https://github.com/0xPiranhaCodes/pinfold.sh/issues/320), [ADR-0045](docs/adr/0045-tools-are-programs-in-their-own-pane.md)). The tool is an ordinary API caller with no extra rights. It lists the panes, then calls `pane.send` to another pane, which the window approves like any cross-pane send, naming the tool pane as the caller and showing the exact text. Meanwhile the tool keeps drawing and says it is waiting, and a denial sends nothing. The target is the pane with the largest `focused` that is not a tool and not the caller, and that has had a status reported from inside it, as agent hooks report one. The text is absolute paths, single-quoted when they hold anything but `A-Z a-z 0-9 . _ / + - @`, each followed by a space, with no newline, so nothing is submitted. A name with a control or bidi character is refused. `pane.list` gains `focused`, an ordering hint rather than a time: larger means the pane took focus in the active tab more recently, and 0 means never. `pane.send` to a tool pane is still refused. `pinfold-tools` now depends on `pinfold-api` and `serde_json`, which the `pinfold` binary already linked.
- `e` in `pinfold files` edits the selected file in `$VISUAL`, else `$EDITOR`, else `vi`, inside the tool's own pane ([#320](https://github.com/0xPiranhaCodes/pinfold.sh/issues/320), [ADR-0045](docs/adr/0045-tools-are-programs-in-their-own-pane.md)). The tool leaves raw mode and the alternate screen, waits for the editor, then takes the terminal back and redraws the whole screen. The editor setting is split into words as a shell splits them, quotes and backslashes included, but nothing is expanded and no shell runs. A bare program name is found only on absolute `PATH` entries, as git is. The file goes last as one absolute argument, so a name holding `;` or quotes is never parsed and one starting with `-` is never an option. `editor.rs` is the only file besides `git.rs` allowed to start a process, and the existing test now says so. No new crates.
- `pinfold files` copies and moves ([#320](https://github.com/0xPiranhaCodes/pinfold.sh/issues/320), [ADR-0045](docs/adr/0045-tools-are-programs-in-their-own-pane.md)). `y` copies and `x` cuts the marked entries, or else the selected one; `p` pastes them into the directory shown, after a confirmation naming both directories and listing every name escaped. Neither replaces an existing name or goes into itself. A link is copied or moved as a link. A move is a rename, refused across file systems rather than copied. A copy has a cap rather than progress and cancel: over 256 MiB or 10,000 entries in all it is refused before anything is written, and a file swapped for a link after the check is caught by its inode. Fifos and devices are not copied. No new crates.
- `pinfold files` renames and trashes, each behind a confirmation drawn in its pane ([#320](https://github.com/0xPiranhaCodes/pinfold.sh/issues/320), [ADR-0045](docs/adr/0045-tools-are-programs-in-their-own-pane.md)). Space marks entries; `r` renames the selected one and `d` trashes the marked, or else the selected. The confirmation lists every name escaped, a flagged one in red, and only a typed `y` carries it out: no API caller can type it, as `pane.send` to a tool pane is refused, and every tool now turns on bracketed paste and drops pasted text, so a paste cannot answer it. A new name holding `/` or NUL, or `.` or `..`, is refused, and nothing ever replaces an existing name. Both act on a link itself, never its target. Trash is a rename into `~/.Trash` on macOS, or the XDG home trash with its `.trashinfo` (written first, to claim the name) elsewhere, under a free name (`name`, `name.2`, ...); on another file system it is refused rather than copied. The `.trashinfo` date is UTC, as std has no time zone. Tests cover rename, trash in both layouts, a refused cross-file-system trash and a confirmation with a hostile name. No new crates.
- `pinfold diff` stages and reverts a hunk ([#323](https://github.com/0xPiranhaCodes/pinfold.sh/issues/323), [ADR-0045](docs/adr/0045-tools-are-programs-in-their-own-pane.md)). On the work tree's diff, `s` stages and `r` reverts the hunk at the top of the view; the pane first shows ◆ with the file name escaped and the hunk header, and only `y` goes on. The patch is the bytes git printed, the file's header and that hunk, uncut even past the 10,000-byte line cap, and is off when the diff was cut short. It goes to the new `git::apply`, `git apply --cached` or `-R` through `run`'s hardening, on standard input so no file is written, and never with `--unsafe-paths`. The diff then reloads, after any watch-mode run in progress, one at a time. A failure shows as ✕ error with git's first line. `nothing_a_hostile_repository_configures_runs` now runs these exact calls, a scratch-repository test stages and reverts the right hunk among several hunks and files, and `an_agent_cannot_type_into_the_tool_it_opened` sends the keys over `pane.send` and checks nothing changed. Sending a hunk to an agent comes in a later PR. No new crates.
- `pinfold files` jumps by fuzzy match and keeps bookmarks ([#319](https://github.com/0xPiranhaCodes/pinfold.sh/issues/319), [ADR-0045](docs/adr/0045-tools-are-programs-in-their-own-pane.md)). `f` lists up to 10,000 paths under the start, breadth first, without following links or entering `.git`, and ranks them as you type: a character scores 1, and 10 more after the last match or else 8 more at the start of a word, so a run beats scattered word starts and a shorter path wins a tie; Enter goes into the best directory, or to the best file in its directory, and Esc leaves. `m x` bookmarks the directory as `x` and `' x` goes back to it; bookmarks last for the run and are never written to disk. No new crates.
- `pinfold files` shows git badges and follows the directory ([#319](https://github.com/0xPiranhaCodes/pinfold.sh/issues/319), [ADR-0045](docs/adr/0045-tools-are-programs-in-their-own-pane.md)). Inside a repository each entry carries `M` (amber), `A` (green) or `?` (cyan) from `git status --porcelain=v1 -z --ignored`, a directory the strongest of what it holds, and an ignored entry is dimmed. Git runs only through `git::run`, on its own thread so a key or a draw never waits on it, and is killed after 2 s, the new `git::run_within` deadline that covers the configuration listing too; past it the status row says so and that directory gets no more calls. Once a second the directory's and `.git/index`'s modification time, length and inode are compared, and only a change lists the directory again, keeping the selection and filter, and reruns git, one call at a time. Outside a repository, found by its `.git`, git never runs. Tests cover each badge from a scratch repository, a hostile status output, the 2 s cap and a file added; a snapshot shows the badges. No new crates.
- `pinfold files` flags hostile names and shows what its caps leave out ([#318](https://github.com/0xPiranhaCodes/pinfold.sh/issues/318), closes [#263](https://github.com/0xPiranhaCodes/pinfold.sh/issues/263), [ADR-0045](docs/adr/0045-tools-are-programs-in-their-own-pane.md)). A name holding a control or bidi character (U+202A-202E, U+2066-2069, U+200E, U+200F, U+061C, C0, C1, DEL) or invalid UTF-8, anything `escape` changes, is drawn escaped in red, and red behind it when selected. The caps of 10,000 entries per directory, with the rest counted on screen, 64 KiB per preview and 4 KiB of hex each have a test that fails without them, and snapshots show flagged names, among them a newline, an ESC and a U+202E, and the cap message. The threat model's T6 row names these tests and #315's. No new crates.
- The built-in tools' one git entry point, `pinfold_tools::git::run`, runs nothing a repository configures ([#262](https://github.com/0xPiranhaCodes/pinfold.sh/issues/262), [ADR-0045](docs/adr/0045-tools-are-programs-in-their-own-pane.md)). It clears every inherited `GIT_*` variable and sets `GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0` and `GIT_NO_LAZY_FETCH=1`; passes `--no-pager` and `-c` overrides for `core.fsmonitor`, `core.hooksPath`, `core.pager`, `core.sshCommand`, `core.askPass`, `credential.helper`, `protocol.allow` and each built-in transport's `protocol.<name>.allow`, which beats `protocol.allow`; reads `git config --list -z` first and empties every `filter.*.clean`, `smudge` and `process` and every `protocol.*.allow` it names, through `GIT_CONFIG_KEY_<n>` since `-c` splits a driver name holding `=`; gives `diff` `--no-ext-diff --no-textconv --no-color`; and gives `diff` and `status` `--ignore-submodules=all`, with `diff.ignoreSubmodules=all` for the rest, since a submodule's own filters are not in the list and `git status` otherwise runs them, even past a submodule's `ignore = none`. Submodule changes do not show. Git is the first executable on an absolute `PATH` entry, so a `git` in the repository is never picked. Git is killed after 10 s and its output kept to 8 MB. `nothing_a_hostile_repository_configures_runs` sets each of these, and a submodule's filter, to a command that leaves a marker, checks plain git runs them, then runs `diff`, `diff --staged`, `status`, `apply --cached`, `apply -R`, `fetch` and `hook run` through `run` and fails on any marker. A repository that needs a filter, such as Git LFS, shows pointer files. No tool calls it yet; the diff viewer ([#321](https://github.com/0xPiranhaCodes/pinfold.sh/issues/321)) will. No new crates.
- `pinfold diff [--staged] [range]` shows a diff: the files on the left, renames as `old → new`, and the selected file's header and unified hunks on the right, added lines green, removed red and hunk headers cyan ([#321](https://github.com/0xPiranhaCodes/pinfold.sh/issues/321), [ADR-0045](docs/adr/0045-tools-are-programs-in-their-own-pane.md)). `n` and `p` pick a file; `j`, `k`, space, `b`, `g` and `G` scroll; `?` lists the keys. Git runs only through `git::run`, with `--src-prefix=a/ --dst-prefix=b/` so a repository's `diff.noprefix` cannot change the paths, and the range before `--`. Output cut short at 8 MB or 10 s, and each parser cap, shows as a yellow banner above the diff; a git error shows as ✕ error with git's first line. Every path and line goes through `Screen::put`, so control and bidi characters show escaped. Snapshots at 80×24 of a unified diff, a hostile path and line, and a cut-short diff complete the tools' snapshots for [#233](https://github.com/0xPiranhaCodes/pinfold.sh/issues/233), and the `unified_diff` fuzz target completes [#235](https://github.com/0xPiranhaCodes/pinfold.sh/issues/235). The "not built yet" placeholder is gone, as every tool is built. No new crates.
- The diff viewer's unified-diff parser takes any bytes without panicking and caps what hostile `git diff` output can cost it ([#321](https://github.com/0xPiranhaCodes/pinfold.sh/issues/321), [ADR-0045](docs/adr/0045-tools-are-programs-in-their-own-pane.md)). It keeps each line as a range into git's output and stops at 10,000 files, 100,000 hunks and 500,000 lines, and cuts a line at 10,000 bytes on a character's first byte; each cap leaves a sentence for the viewer's banner and has a test that fails without it. A line that looks like a header stays in its hunk. Paths come from `---` and `+++`, `rename` and `copy` lines and the `diff --git` line, with git's C-style quoting undone to the path's bytes, so the screen escapes them as it escapes file names. - `pinfold md` caps what a hostile file can cost it ([#315](https://github.com/0xPiranhaCodes/pinfold.sh/issues/315), [ADR-0045](docs/adr/0045-tools-are-programs-in-their-own-pane.md)). It opens the file without blocking, through the new `pinfold_sys::open_nonblocking` (O_NONBLOCK and O_NOCTTY), so a FIFO or device cannot hang it, refuses one that is not a regular file, and reads at most 5 MB and one byte more, without trusting the file's length; a longer file shows its first 5 MB as plain text. Parsing stops after 2 s at each width and the rest shows as plain text, laid-out lines stop at 100,000, and code, table and plain-text lines are cut at 10,000 characters. A yellow banner above the file says which cap cut it. Each cap is a constant with a test that fails without it, a test checks each escape in file content as markdown and as plain text, and a snapshot shows the banner. The new `markdown` fuzz target, with seeds in `fuzz/seeds/markdown/`, joins `cargo xtask fuzz-smoke`. No new crates.
- `Screen::put_link` draws OSC 8 links whose targets come from untrusted files ([#314](https://github.com/0xPiranhaCodes/pinfold.sh/issues/314), [ADR-0045](docs/adr/0045-tools-are-programs-in-their-own-pane.md)). `link_target` allows only `http`, `https` and `file` URIs, percent-encodes every byte outside printable ASCII, so no control, DEL, ESC, BEL or ST (U+009C) can end the sequence, and refuses a target over 2,048 bytes once encoded, the core's `MAX_URI`; a refused target draws as plain text. The writer opens a link where its cells start, closes it before the next cell or at the end of the row, and redraws every row when the targets change. A test per rule. A sandboxed agent cannot open a tool, which would run outside its sandbox. `an_agent_cannot_type_into_the_tool_it_opened` opens a tool from a pane, sends to it, makes six refused calls, closes it and checks the other shell pane still echoes what it is sent.
- On Linux a protected pane no longer reads as unprotected while a program is starting ([#336](https://github.com/0xPiranhaCodes/pinfold.sh/issues/336)). An empty `cmdline` now reads as none, the name and user are read on both sides of the arguments and must agree, and both cases get the 4 tries 1 ms apart macOS already had, then read as unreadable, which protects the pane. - A sandboxed agent no longer gets environment variables whose names look like secrets ([#328](https://github.com/0xPiranhaCodes/pinfold.sh/issues/328), [ADR-0041](docs/adr/0041-sandbox-hides-writes-not-secrets.md)). - On macOS a sandboxed agent can no longer start a program outside its sandbox ([GHSA-f24m-hqgq-vp7v](https://github.com/0xPiranhaCodes/pinfold.sh/security/advisories/GHSA-f24m-hqgq-vp7v)). Under the new rules `python3`, `node`, `git`, `claude` and `curl` still run. Linux is not affected.

### Fixed

### Fixed

- macOS: frames share one Metal instance buffer, so the window's idle memory reads steadily.
  The window budget rises to 33 MB plus pixels (ADR-0030).
- A core test that failed on macOS when its stand-in window had already ended.
- `pinfold` waits until the window is on screen, and fails with a short reason if the window cannot run, ends during start or is not ready in time: 10 seconds for a core's first window, so a slow Mac does not report failure for a window that opens, and 2 seconds after that. It used to exit 0 once the process existed, and said only "no window can open".
- Bold `i` and other glyphs of several contours no longer come out thinner than regular.
- A paste or a key no longer vanishes while the core lags. The window waits for the link in order, holding at most about 3 MiB, and past that says so under the pane, as it does for input a stalled program has no room for. A paste over the 1 MiB limit, less its brackets, is refused with a note instead of going missing. The link's version is now 4.
- Fallback font pages no longer count against the window once a frame is drawn.
- A copy of a whole pane can run in steps, which keeps its text out of the core's footprint.
- A core started by `pinfold`, and its windows, write problems to `default.log` in the runtime directory, so a window that dies says why even from the Dock, and a failed `pinfold` names the file. It is private, starts empty with each core, and a panic there prints only its place, as a panic's text can quote a pane.
- A window taller than 24 rows no longer costs the core about 2 MB, as growing a grid makes only the rows it needs.
- The core sends a window only the panes it asked for, so a hidden pane holds no frame.
- The config file is `pinfold.toml`, the name the design gives it.
- Closing a pane with unread output can no longer hang on macOS.
- A window narrowed to one column with a wide character on screen no longer exhausts memory.
- An unterminated OSC string can no longer grow the core without limit.
